# Results

Everything in this directory is evidence. Two kinds of file live here, and they are treated
differently.

## Ours — kept in English

Reports we wrote about our own measurements: `bench-qa.md` (generated by
`bench-qa.mjs`), `e1-agent-browser.md`, `e2-contracts.md`, `e4-where-they-win.md`,
`e5-coexistence.md`, `abis-verbs.md`, `c-false-green.md`, `claude-vs-chrome.md`, and the
files under `../formal/results/`. `value-focal.md` preserves one historical schema-1
observation and five descriptive schema-2 Playwright Test/SnapDOM observations. The
historical schema-1 raw data lives in `value-focal.json`; the aligned schema-2 run and
four immediate repetitions live in `value-focal-v2.json` and
`value-focal-v2-rep2.json` through `value-focal-v2-rep5.json`. Both arms passed 6/6 in
schema 1 and 30/30 in schema 2, but these observations are not a throughput benchmark or
causal speed claim. The current `../value-focal.mjs` emits schema 2.

The first schema-2 attempt exposed the missing `disabled:false` state-evidence endpoint.
It was fixed and the complete exact rerun was published as `value-focal-v2.json`. The
failed raw attempt stays in the local `work/` area for diagnosis and is not claimed as a
result in this directory.

`mcp-value.md` and `mcp-value.json` are the generated report and raw protocol record for
the hermetic MCP-to-MCP probe in `../mcp-value.mjs`. Across the same 24 local trials per
arm (four postconditions, correct and near-miss variants, three repetitions), Playwright
out of the box, SnapDOM direct assertion, and Playwright custom evaluation each matched
the frozen expected-truth manifest 24/24, with no false green, false negative, or
`UNKNOWN`. This establishes equal correctness only on those authored fixtures. SnapDOM
used one uniform declarative verification call; Playwright used zero to two out-of-box
calls or one custom-JavaScript call and was smaller in median effective bytes. The report
keeps direct and escape-hatch routes separate, exposes short-circuit rounds per case,
and includes full-flow setup + action + verification costs.

`client-side-footprint.json` records deterministic bundle/package sizes for the
browser-only observer, companion runtime, raster-enabled SDK, and the all-in-one
development package. `client-side-egress-v2.json` is the companion selective-evidence
experiment: it applies one exact pre/post contract to whole-body ARIA snapshots and the
client-side companion, includes each reader's baseline, balances order, and references
80 verbatim bodies in `client-side-egress-v2.artifacts.json.gz`. Its synthetic large-page
result supports selective evidence egress, not a speed, token, or incremental-compute
claim. `client-side-egress-v2.directional-audit.json` deterministically re-reads those
bodies and verifies the authored transition in the correct direction, including
SnapDOM's `beforeName` to `name` fields, rather than accepting mere substring presence.
The uncertainty stress also records that uncapped `unobservableDetails` grows the
response as blind regions increase. `client-side-attention.json` is retained as the
superseded preliminary run; it excluded SnapDOM's baseline and used asymmetric truth
checks, so do not use it for the headline numbers.

`client-side-egress-v3.json` repeats the protocol against the packed and installed
browser SDK. Its 96 exact retained bodies show the official receipt stayed at 1,059 B
while the ARIA post body grew from 5,766 B to 356,766 B. The SDK baseline itself grew
from 22,777 B to 1,390,087 B, making the full SDK cycle roughly 1.95–2.07× the two ARIA
bodies. The supported claim is therefore local heavy state plus small post-action egress,
not a smaller total cycle. Its capped uncertainty receipts report totals/truncation and
remain below 1,900 B through 300 authored blind regions. The first v3 attempt is recorded
as discarded because its harness incorrectly rejected `possible-replacement` evidence.

`directed-host-receipt-value.json` compares the same four predicates with and without the
receipt. Both arms scored 15/20 with zero false greens and five `UNKNOWN`; the receipt
added a standard diagnostic envelope but no correctness. `schema-drift-receipt-value.json`
then compared a reusable generic host with the SDK across five variants. The host was
exact 15/15; the SDK 9/15, losing endpoint state/content on legitimate semantic changes.
The SDK block was shorter (17 versus 64 runtime LOC), but both required zero
variant-specific adapters, so no maintenance advantage is claimed.

`resident-sensor-value.json/.md` preserve the first development probe of the resident
scope architecture. That run found that shadow-root discovery still scanned the entire
sensor root, causing renderer p50 growth of 160.71% from 100 to 10,000 exterior labels.
The code was narrowed to discover shadows only inside the paid scope, and
`resident-sensor-value-v2.json/.md` record the corrected single descriptive run. Across
90 windows over a fixed 54-element scope, every report contained exactly the two planted
directional effects and was exactly 2,507 B; renderer mark+read p50 was 2.010–2.409 ms
and diagnostic V8 retained-heap p50 was 76,660 B. This is a scoped-attention architecture
check, not a speed, constant-time, browser-wide, or commercial-superiority claim.

`multisite-review-v2.json` and `.md` re-score the currently available assignments,
responses, review key, and pilot after the original v1 source links became stale. The
result remains `HELPER_ONLY`. The assignments/responses still live outside this repo, so
v2 is not an immutable raw archive. It is an identity-redacted evidence-clarity review
whose reviewers saw prepared verdict/check material, not a test of autonomous diagnostic
discovery.

The standalone `packages/sensor/` now emits `@zumer/snapdom-sensor`, a three-export
standard SnapDOM plugin package. It declares SnapDOM v3 as its peer, keeps its prior-state
graph private across scoped SnapDOM captures, and emits a descriptive, bounded
`toSensor()` report with `taskAssessment.status: NOT_ASSESSED` and
`causality.status: NOT_ESTABLISHED`.
`browser-sdk/` remains the portable-receipt compatibility path, where
`PASS | FAIL | UNKNOWN` applies only to the declared `changed` postcondition. The v3
egress result above measures that older portable path; resident V1/V2 measured an
abandoned standalone `mark/read` prototype and must remain historical rather than being
relabeled as measurements of the standard plugin.

## Somebody else's — kept in the original language, unedited

`codex-self.md`, `codex-self-v2.md` … `codex-self-v5.md`, `codex-mcp.md`,
`codex-assert.md`, `codex-f3-privacy.md`.

These are the reports an outside reviewer wrote in the first person about our tool,
including the parts where it came off badly. **They are not translated and not edited.**
Rewriting somebody else's assessment — even only into another language — turns primary
evidence into our paraphrase of it, and the whole value of those rounds is that we did not
write them. Some are in Spanish and some in English, depending on the round; that is how
they arrived.

If a claim from one of those reports matters, quote it and say it is a quotation, rather
than folding it into our own prose.

## The JSON files

Raw per-case data next to each report, gitignored except where a report cites it. The six
focal JSON files are intentionally cited evidence. Regenerate with the command listed at
the bottom of the matching report, and store a new observation instead of overwriting a
published run.
